# Audit — Audio
**Scope:** AudioInputEngine.swift, AudioLevel.swift, AudioSessionCoordinator.swift, ClickSound.swift, FirstRunFlag.swift, InputLevelMeter.swift, MetronomeEngine.swift, MicrophonePermission.swift, PitchDetector.swift, ToneGenerator.swift, ToneOscillator.swift

**Health:** The pure-math layers (AudioLevel, ToneOscillator, ClickSound, MetronomeSequencer usage) are clean, well-guarded, and genuinely testable. The hardware wrappers are mostly sound, but there are two real concurrency/real-time hazards (a cross-thread data race on the tone-generator render state, and unbounded `Task`-per-buffer hops from audio threads) plus several session-lifecycle and inefficiency issues. Nothing here is catastrophic, but the tone-generator race and the audio-thread `Task` allocations deserve attention.

## Bugs & correctness
- [BUG|HIGH] `ToneGenerator.swift:144,147,162,255` — `generator`, `envelopeTarget`, and `envelopeGain` are `nonisolated(unsafe)` but are mutated from the **main actor** (`play()` calls `generator.setFrequency(...)` and sets `envelopeTarget`; `stop()` sets `envelopeTarget`) **while** the render callback is concurrently reading/mutating the very same fields on the audio thread. The convention you whitelisted is "fields touched *only* by render callbacks" — these are touched by both, so the documented invariant ("we never read them back on the main actor while audio is running") does not actually hold. `generator` is a two-field struct (`phase` + `phaseStep`); a non-atomic struct write torn against a concurrent render read can produce a corrupted phaseStep (audible glitch/wrong pitch) and is UB under the memory model. Fix: make the render→main handoff explicit — store the target frequency / target gain in `atomic`-style scalars (e.g. a single `Float` `pendingPhaseStep` written main-side, read render-side; envelope targets are already scalar `Float` so they're far less dangerous, but `generator.setFrequency` is the real offender). Simplest: have `play()` write only a scalar `nonisolated(unsafe) var pendingPhaseStep`, and let the render callback apply it to its own `generator`.
- [BUG|MED] `MetronomeEngine.swift:266-269` — the "buffer failed to synthesize" safety net re-invokes `scheduleNextTick()` from inside the *previous* `scheduleNextTick` via a `Task { @MainActor }` with **no delay and no scheduled-audio anchor**. If `rebuildBuffers()` produced `nil` buffers (e.g. format with 0 channels, or alloc failure) every tick hits this path and you get an unbounded immediate recursion advancing `nextTickToSchedule` as fast as the main actor can spin — a busy-loop, not a click. The muted case correctly uses `silentBuffer` so this only triggers on real synthesis failure, but it should bail/stop the engine after N consecutive nil buffers rather than spin.
- [BUG|MED] `AudioInputEngine.swift:189` & `AudioSessionCoordinator.swift` — session ownership is split. `AudioInputEngine.start()` sets the `.record` category and calls `setActive(true)` itself (line 130-131), and `stop()` calls `setActive(false)` (line 189), yet the PRD says the coordinator owns category switching. When both a `ToneGenerator`/metronome path (coordinator → `.playback`) and the mic engine are alive, `AudioInputEngine.stop()` will `setActive(false)` out from under a tone that's still fading, and `start()` will silently flip the shared session back to `.record`/`.measurement`, overriding whatever the coordinator just set. This is the exact "stomp on each other" hazard the coordinator file warns about (lines 16-21) — the mic engine should NOT touch the session at all; route it through the coordinator.
- [BUG|LOW] `MetronomeEngine.swift:160-164` — `shutdown()` calls `engine.stop()` but never `engine.detach(player)` (contrast `ToneGenerator.shutdown()` which detaches its source node). On a later `start()`, `setUpIfNeeded()` guards on `isSetUp` which is now `false`, so it will `engine.attach(player)` a *second* time on the same already-attached player node — `AVAudioEngine` will assert/throw on re-attaching a node it already owns. Re-entering the metronome tool after leaving it can crash. Fix: detach the player in `shutdown()`, or don't reset `isSetUp` if you keep the graph.
- [BUG|LOW] `MicrophonePermission.swift:110-122` — `request()` is `@MainActor`-isolated, but `withCheckedContinuation`'s completion (`requestRecordPermission`) "may arrive on a background thread" (your own comment line 108-109). After `await`, execution resumes back on the main actor automatically, so the final `state = ...` is fine — but the inline comment claiming you "hop back with `await MainActor.run`" is stale/wrong (there is no `MainActor.run` here). Not a runtime bug, but the comment misdescribes the safety mechanism in a learning project. (Doc nit, but flagging because the comment asserts a guarantee the code doesn't implement.)

## Efficiency / real-time safety
- [REAL-TIME|HIGH] `AudioInputEngine.swift:164` & `PitchDetector.swift:245` & `MetronomeEngine.swift:266,278` — every tap buffer / pitch buffer / tick completion spawns a `Task { @MainActor in ... }` **from a real-time audio thread**. `Task` creation allocates and enqueues onto the cooperative pool; doing this in (or immediately downstream of) a render/tap/completion callback is exactly the allocation-on-the-audio-thread pattern that causes priority inversion and glitches. The tap fires ~10×/s so it's survivable, but the metronome completion path and the source-node-adjacent hops are hotter. Prefer a lock-free ring buffer / `AtomicLevel` the main actor polls, or `DispatchQueue.main.async` is marginally cheaper than `Task` but still allocates — the principled fix is to not touch the actor from the callback at all.
- [REAL-TIME|MED] `AudioInputEngine.swift:201-210` (`samples(from:)`) and `PitchDetector.swift:242` — `Array(UnsafeBufferPointer(...))` **heap-allocates a fresh `[Float]` of `frameLength` (4096) on the audio thread** for every buffer, then captures it into the `Task`. Allocation on the tap thread is a documented real-time no-no. For the tap path you could compute RMS in-place on the pointer (no copy) and only hop a scalar; the pitch path genuinely needs the samples but could reuse a preallocated buffer.
- [EFFICIENCY|MED] `ClickSound.swift:66-70,91-95` — the channel-copy is a nested Swift `for` loop writing element-by-element (`channelData[channel][i] = mono[i]`). For multi-channel formats this is O(channels·frames) scalar stores. Use `memcpy`/`update(from:)` per channel, or better, synthesize once and `memcpy` into each channel pointer. Cheap since it's per-start, but it's the same pattern repeated in two near-identical functions (see maintainability).
- [EFFICIENCY|LOW] `AudioLevel.swift:52-54` — `reduce` summing squares is fine but `vDSP_rmsqv` (Accelerate) would be both faster and more numerically stable for 4096-sample buffers; you already import nothing that precludes it. Optional.

## Maintainability & practices
- [MAINT|MED] `ClickSound.swift:56-72` vs `:83-97` — two `buffer(format:...)` overloads contain an **identical** channel-copy loop (lines 64-70 ≡ 90-96). The `frequencyHz` overload should just call `buffer(format:samples:)` with `samples(...)`, eliminating the duplicate loop (and giving you one place to apply the `memcpy` fix above).
- [MAINT|MED] Session handling is duplicated three ways: `AudioInputEngine` inlines `.record/.measurement/.duckOthers` (line 130) that the coordinator *also* defines (`configureForRecording`, line 60). They must be kept in lockstep by hand. Collapse to one source of truth (the coordinator) — this also resolves the ownership bug above.
- [MAINT|LOW] `MetronomeEngine.swift:202-205` — the silent-buffer length falls back to `format.sampleRate * 0.03` magic constant duplicating `ClickSound.samples`' default `durationSeconds: 0.03`. If you ever change the click duration, these silently diverge. Reference a shared constant.
- [MAINT|LOW] `AudioInputEngine.swift:92` comment says the handler is "set once (before `start()`) and only read afterward," but `onBuffer(_:)` (line 104) is public and unguarded — nothing prevents a caller from re-registering after `start()`, which would be a main-thread write racing the audio-thread read. Either assert `!isRunning` in `onBuffer`, or document/enforce the contract.
- [NIT] `ToneOscillator.swift:207` — `let twoPi = Float.pi * 2` is recomputed inside `nextSample()` on every sample (called per render frame). Hoist to a `static let`. Trivial, but it's in the hottest loop in the file.

## Test coverage gaps
- No test can catch the `ToneGenerator` data race (it's nondeterministic) — but a test that calls `play` → `play(differentFreq)` → `stop` rapidly while the engine renders would at least exercise the retarget path; consider a deterministic unit test of an extracted "apply pending frequency" step.
- `MetronomeEngine` restart/shutdown sequencing (the double-attach crash, `BUG|LOW` above) is integration-only and currently untested — a test that does `start()/shutdown()/start()` would surface it without audio assertions if `setUpIfNeeded` is made observable.
- `AudioInputEngine.samples(from:)` has a `guard ... return []` for non-float buffers and a multi-channel assumption (only channel 0) — neither is covered; a fabricated `AVAudioPCMBuffer` test would pin the empty-on-nil and frame-count behavior.
- Pure layers (`AudioLevel`, `ToneOscillator`, `ClickSound.samples`, `MetronomeSoundSet.samples`) are the well-testable parts and appear designed for it — confirm the distinct-peak-frequency assertions per sound set actually exist (the comments promise them).

## Top 3 priorities
1. Fix the `ToneGenerator` cross-thread data race on `generator`/`envelopeTarget` (HIGH) — main actor mutating render-thread state violates the stated `nonisolated(unsafe)` invariant; hand off via a single scalar.
2. Stop allocating (`Task` + `[Float]` copy) on audio threads in the tap / pitch / metronome-completion callbacks (HIGH real-time) — move to lock-free scalar handoff the main actor polls.
3. Centralize `AVAudioSession` ownership in `AudioSessionCoordinator` and stop `AudioInputEngine` from setting/deactivating the session itself (MED) — fixes the record↔playback stomp and the double-attach crash in `MetronomeEngine.shutdown()`.
