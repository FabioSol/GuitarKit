# Audit — Domain (Fretboard / Instruments / Metronome / Tuning)
**Scope:** Fretboard/{Fretboard.swift, FretboardScale.swift}; Instruments/{Instrument.swift, InstrumentLibrary.swift, CustomTuningSupport.swift}; Metronome/{MetronomeSequencer.swift, TimeSignature.swift, Subdivision.swift, BeatAccent.swift, TapTempo.swift}; Tuning/{TuningSession.swift, TuningFeedback.swift, BuiltInTuning.swift}. (Supporting types read for verification: Note.swift, Scale.swift, Capo.swift, PitchCalculator.swift.)

**Health:** The math cores are largely sound — the drift-free sample/tick scheduler, the cents-based tuning state machine, and the scale-membership projection are all correct and well-tested. The defects that exist are mostly state-consistency and inefficiency issues at the edges (a stale-deviation leak on `clearLock`, full board re-scans, an unanchored fretboard-range assumption with capo). No catastrophic correctness bug, but several MED issues affect what the UI shows, and a couple of API inconsistencies will bite when the metronome's denominator finally matters.

## Bugs & correctness
- [BUG|MED] `TuningSession.swift:137-140` — `clearLock()` clears `inToleranceSince` and `isManuallyLocked` but **leaves `deviationCents` (and therefore `zone`) stale**, whereas `lock(toStringIndex:)` (`:133`) deliberately clears `deviationCents = nil`. Why it matters: after releasing a lock the readout/needle keeps showing the old deviation and zone until the next `update`, so a UI sampling `zone`/`deviationCents` right after `clearLock` paints a phantom in-tune/flat state, and `tuningFeedbackEvent(from:to:)` can mis-fire on the next transition. Fix: set `deviationCents = nil` in `clearLock` to mirror `lock`.
- [BUG|MED] `Fretboard.swift:50` — `note(string:fret:)` rejects `fret > fretCount`, but with a capo the *playable* range shrinks: a capo at fret N still lets `fret` run `0...fretCount`, so the top sounded note is `open + N + fretCount` semitones — i.e. the board effectively extends N frets past the real instrument. Conversely there's no way to address the open (un-capo'd) string. Why it matters: `FretboardScale.ascendingNotes()` (`:55`) iterates `0...fretCount` and will emit notes N semitones above the highest real fret when a capo is set, so the "play ascending" sequence contains pitches the player can't actually fret. Fix: decide whether `fretCount` is physical (then clamp the usable range to `fretCount - capo.fret`) or capo-relative, and document/enforce it; the tests don't pin this.
- [BUG|LOW] `TuningSession.swift:127-134` — `lock(toStringIndex:)` does not clear `latchedStrings` or `justLatchedStringIndex`, and `update` (`:186-189`) will happily re-run the hold/latch path on an already-latched locked string. `latch` (`:204`) guards re-insertion so it's idempotent, but `justLatchedStringIndex` is only set inside `latch`'s guarded body, so this is benign today — flagging because the "lock onto an already-latched string" path is untested and one refactor away from re-firing the one-shot event.
- [BUG|LOW] `Instrument.swift:165` / `:170` — `stringCount` and `defaultTuning` silently treat an empty `tunings` array as `0`/`nil`. The "all presets share the count" invariant is test-enforced (`InstrumentLibraryTests:49`), but nothing enforces `tunings` non-empty, and a custom/empty `Instrument` would make `CustomTuningSupport.outOfRangeStringIndices` (`:109`) flag nothing and `Fretboard(tuning:)` build a 0-string board with no error. Fragile assumption rather than an active bug.

## Efficiency
- [MED] `FretboardScale.swift:52-67` — `ascendingNotes()` does a full `stringCount × (fretCount+1)` board scan building a `Set<Int>`, and `descendingNotes()` (`:65`) calls it *again* and reverses, doubling the work. Neither result is cached, and `FretboardScale` is an immutable value, so every call recomputes from scratch. For a 7-string × 15-fret board that's ~120 `note()`+`cents`-free lookups per call; cheap individually but called per render/playback. Consider computing once (lazily or in `init`) and deriving descending by `reversed()` on the stored array.
- [LOW] `TuningSession.swift:215-222` — `nearestStringIndex(to:)` recomputes `PitchCalculator.cents(...)` for *both* operands inside every `min` comparison closure, so each target's cents is evaluated O(log n)–O(n) times instead of once. For ≤7 strings it's negligible, but it's an O(n·log n) `log2` call pattern where an O(n) single-pass min-by-key would be clearer and cheaper. Same value-recompute smell as the fretboard scan.

## Maintainability & practices
- [MED] API inconsistency across the metronome: `TimeSignature.noteValue` (`TimeSignature.swift:54`) is carried but **never consumed** by the timing math, and `MetronomeSequencer` (`:73`) defines a "beat" purely from BPM with no denominator awareness. This is documented as intentional (6/8 = six clicks), but it means BPM silently means "quarter-note BPM" for 4/4 and "eighth-note BPM" for 6/8 — the same numeric tempo produces different real-time pulse rates across signatures. When the denominator eventually matters, the seam doesn't exist. At minimum, surface the assumption in `samplesPerBeat`'s doc, not only `TimeSignature`'s.
- [LOW] Access-level inconsistency: the Tuning, Fretboard, Instruments, and PitchCalculator types are `public`, but the entire Metronome group (`MetronomeSequencer`, `TimeSignature`, `Subdivision`, `BeatAccent`, `TapTempo`) and `BuiltInTuning` are `internal`. If "Domain" is meant to be a uniformly testable/consumable layer, the split is arbitrary and will surface as visibility friction if the module is ever split.
- [LOW] `BuiltInTuning.swift` is explicitly marked a placeholder to be folded into `InstrumentLibrary`, yet `InstrumentLibrary.guitar6` (`InstrumentLibrary.swift:80`) now duplicates the exact EADGBE sequence. Two sources of truth for standard guitar; delete `BuiltInTuning` and repoint callers (`grep` shows `TuningSession`/tuner code still reference it).
- [NIT] `CustomTuningSupport.outOfRangeStringIndices` (`:103`) compares against `defaultTuning` by **same index**, but for instruments whose presets differ in *octave layout* this is fine only because all presets share a count; if the edited set is shorter than home, the trailing home strings are silently unjudged (`:116` `where index < home.strings.count`) — acceptable per the "warn, don't block" spec but worth a doc line that under-length sets are partially judged.
- [NIT] `FretboardScale.degree` (`:46`) relies on `scale.notes` having no duplicate pitch classes (true for all current `ScaleType`s). Safe today; a future scale recipe with a repeated pitch class would make `firstIndex` ambiguous. A comment asserting the recipe invariant would harden it.

## Test coverage gaps
- **Fretboard + capo range**: `FretboardTests` covers capo transposition (`:43`) but not the capo/`fretCount` interaction above — no test pins what the top playable fret is, nor that `ascendingNotes()` stays within the instrument under a capo. This is exactly where the MED bug hides.
- **`FretboardScale.ascendingNotes/descendingNotes`**: `test_ascendingNotes_areSortedAndInScale` exists, but there's no dedup test (a pitch reachable on multiple strings appearing once) and no `descending == reversed(ascending)` test, and none with a capo.
- **`TuningSession.clearLock`**: 16 session tests, but none assert post-`clearLock` state — the stale-`deviationCents` bug ships untested. Add a test that locks, reads deviation, clears, and asserts `deviationCents == nil` / `zone == nil`.
- **`TuningSession` lock-onto-latched**: no test for locking a string that's already latched (the LOW one-shot-event concern).
- **`TimeSignature.noteValue` semantics**: presets/clamping are tested, but nothing documents/tests that timing ignores `noteValue` — a regression test would freeze the intentional scope decision.
- **`Instrument` empty-tunings guard**: `stringCount`/`defaultTuning` fallbacks (`:165`,`:170`) are untested; one test constructing an empty-tunings `Instrument` would pin the defensive behavior.
- **`Subdivision`/`BeatAccent`**: `next` cycle and `ticksPerBeat` are covered; no gap of note.

## Top 3 priorities
1. **Fix `TuningSession.clearLock` to clear `deviationCents`** (`TuningSession.swift:137`) and add a regression test — user-visible phantom-state bug, one-line fix.
2. **Resolve the Fretboard capo/`fretCount` range ambiguity** (`Fretboard.swift:50`, `FretboardScale.swift:55`) so `ascendingNotes()` can't emit unplayable pitches under a capo; cover with a capo-range test.
3. **Cache `FretboardScale.ascendingNotes()`** (compute once, derive `descendingNotes` by `reversed()`) to kill the double full-board re-scan per call.
