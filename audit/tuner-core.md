# Audit — Tuner core
**Scope:** GuitarKit/Tuner/{TunerView, TunerHeroView, TuningSessionModel, CentsMeterView, MicDeniedView, MicPrimingView, RawPitchReadoutView}.swift; Tuner/Headstock/{HeadstockSpec, HeadstockLayout, HeadstockView}.swift; Tuner/Visualization/{TunerDevConfig, TunerDevPanelView}.swift

**Health:** The slice is well-structured at the leaf level — the pure session is cleanly wrapped, views are mostly dumb functions of state, and the audio collaborators are thin. The real risk is concentrated in `TunerView`, a genuine god-object that owns 11 `@State` objects and hand-wires every mode transition through ad-hoc `.onChange` handlers; several of those transitions have correctness gaps (chromatic teardown, unconditional sheet-dismiss restart, scene-phase engine restart). No crashers, but the mode matrix (tone × chromatic × sheet × scenePhase) is under-specified and untested.

## Bugs & correctness
- [BUG|MED] `TunerView.swift:245` — `.sheet(onDismiss:)` unconditionally calls `syncToneMode(false)` regardless of whether tone-mode was ever entered. On every picker/editor dismiss this calls `toneGenerator.shutdown()` and `syncEngine(to:.granted)`, which tears down and **restarts the whole mic engine** (new tap install, session re-activation) even though nothing changed. Why: the handler was written for the editor's tap-to-hear playback case but fires for the common picker path too. Fix: only restore if playback was actually engaged, e.g. guard on `toneGenerator.isPlaying || isToneMode`, or track an explicit `didEnterPlayback` flag set by `handleHearNote`.
- [BUG|MED] `TunerView.swift:239-241` — leaving chromatic mode does nothing. Entering it forces tone-mode off, but on chromatic→off the `session` is never reset/re-synced, so it ingests again from wherever it was left (stale `previousZone`/latches, possibly mid-completion) and the detector keeps whatever smoothing state it had. Why: only the `on` edge is handled. Fix: on `!on`, call `session.reset()` (or at least clear stale active string) so targeted tuning resumes clean.
- [BUG|MED] `TunerView.swift:150-153` — `scenePhase == .active` calls `permission.refresh()` but never re-syncs the engine when permission was already `.granted`. Returning from background where iOS interrupted/stopped the engine (phone call, another app grabbed the mic) leaves `permission.state` unchanged at `.granted`, so the `.onChange(of: permission.state)` never fires and the mic stays dead with no readings. Why: engine restart is keyed only off permission *changes*, not foreground. Fix: on `.active`, if granted and not in tone-mode, `syncEngine(to: .granted)` (start() is idempotent) or observe `AVAudioEngineConfigurationChange`/interruption notifications.
- [BUG|LOW] `TunerHeroView.swift:86-88` — completion flourish uses `DispatchQueue.main.asyncAfter` with no token/cancellation. Rapidly toggling in/out of completion (or leaving the view) leaves the 0.6s closure pending; it then flips `celebrate=false` on a possibly-recelebrating or torn-down state, and overlapping fires can fight. Low impact (cosmetic, self-correcting) but it's an uncancelled timer reaching back into view state. Fix: use a `Task` stored in `@State` and cancel on re-entry/`onDisappear`, or animate via a phase the body derives.
- [BUG|LOW] `TunerView.swift:387-390` `playingStringIndex` matches the tone generator's frequency against `session.targets` by `abs(diff) < 0.01`. When two strings share a target frequency (e.g. some custom/alternate tunings, or capo collisions) `firstIndex` highlights the wrong/first peg. Minor, but worth an index-based source of truth (have the parent remember which peg index it told the generator to play).
- [NIT] `TunerView.swift:413` `handleHearNote` uses `try?` and silently drops a playback-configure failure, while the structurally identical `syncToneMode:401` logs it. Inconsistent error handling for the same operation.

## Efficiency
- `TunerView.swift:281-295` — eight separate `#if DEBUG` `.onChange(of:)` modifiers each call the same `applyDevOverrides()`, which on every knob change rebuilds the entire `TuningSession` (re-derives all targets) *and* reconfigures the detector. Acceptable for a dev panel, but it means dragging one slider thrashes the session; a single debounced apply would be cleaner.
- `TunerView.swift:144-146` + `:287-294` — many fine-grained `.onChange` observers attached to the body. Each is cheap individually, but they all live on the god-view; decomposition (below) would localize them.
- `HeadstockView.swift:119-134` `stringLines` rebuilds a `Path` every body pass from `spec.pegs`. Fine at this scale, but it's pure geometry recomputed on every tuning-state re-render (which happens at detector cadence). Could be memoized on `spec`/size.
- `TunerView.swift:184-193` `ChromaticReadoutView(reading: detector.reading)` is built as the `back` of `HeroFlip` even when not flipped; confirm `HeroFlip` lazily defers the hidden side, otherwise the chromatic readout re-renders on every detector reading even in targeted mode.

## Maintainability & practices
- **God-object (primary finding).** `TunerView.swift` owns 11 `@State` collaborators (permission, engine, detector, session, toneGenerator, coordinator, selection, customTunings, devConfig, + flags) and is simultaneously: permission state machine, audio-mode orchestrator, sheet router, settings applier, dev-panel host, and peg-tap router. The mode logic (`syncEngine`, `syncToneMode`, chromatic/tone interlock, scenePhase) is the part most prone to the bugs above and should be extracted into a dedicated `@Observable TunerCoordinator`/`TunerModeController` that owns engine+detector+tone+coordinator and exposes intent methods (`enterToneMode()`, `enterChromatic()`, `foregrounded()`). That object is unit-testable; the view becomes presentation. The mode interlocks (tone↔chromatic↔record↔playback) are currently expressed as scattered one-edge `.onChange`s rather than one explicit state machine — that's the root cause of the chromatic-teardown and sheet-dismiss bugs.
- `RawPitchReadoutView.swift` — **dead code.** Not referenced anywhere outside its own file (superseded by `ChromaticReadoutView`); its header still calls it "slice #03". Either delete or document it as a kept reference preview.
- `HeadstockSpec.spec(for:)` fallback logic is duplicated: `TuningSessionModel.swift:226-233` and `HeadstockSpec.standardGuitar:63-69` both implement "load JSON else procedural fallback" with different aspect-ratio defaults (0.66 appears in both as a magic literal). Centralize on one `HeadstockSpec.load(for: instrument)`.
- `holdDuration: 0.7` and `perfectCents: 1` are hardcoded in **two** places (`applySettings:438` and `applyDevOverrides:507`). The dev-override path silently re-bakes these; if the standard tolerance changes they'll drift. Extract a tolerance builder.
- `HeadstockLayout` x-columns `0.24/0.76` (`:42-49`) and the `stringLines` nut span `0.38…0.62` (`HeadstockView.swift:127`) are independent magic numbers that must visually agree with `HeadstockShape`'s hand-tuned bezier — fragile coupling with no shared constant.
- `CentsMeterView` `range = 50` and the `0.10` detent width are magic numbers; the detent band width (10%) does not derive from the actual ±3¢/tolerance window, so the visual "in tune" band and the logical in-tune zone can disagree.

## Test coverage gaps
- **`TunerView` mode-transition logic is entirely untested** — there is no `TunerViewModelTests`/coordinator test (none found under GuitarKitTests/Tuner). The exact transitions that carry the bugs above (tone enter/leave, chromatic interlock, sheet-dismiss restore, scenePhase restart, permission→engine sync) have zero coverage. Extracting a coordinator (above) is the prerequisite to testing them.
- `TuningSessionModel` is deliberately untested (documented), but its haptic *edge-firing* (`fireHaptics` enter-perfect/in-tune/latched/completed one-shot semantics, `:129-153`) is real branching logic with a fake-haptics seam already in place — it should have a test with an injected `TuningHapticsProviding`.
- `TuningSessionModel.spec(for:)`/`reconfigure`/capo `rebuildSession` reset behavior (clearing `previousZone`/`wasComplete`) is untested; a regression here silently breaks haptics edge-detection.
- `HeadstockLayout.generic(stringCount:)` (the 4/5/7/8-string fallback math, including the `perSide`/reversed-column ordering) has no test despite being the seam slice #09 grows into — only `HeadstockSpecTests` exists.
- `CentsMeterView.indicatorX` clamping/fraction math and `centsLabel`/`accessibilityLabel` sign formatting are pure and trivially testable but untested.

## Top 3 priorities
1. **Extract a testable `TunerCoordinator` / mode state machine** out of `TunerView`, consolidating engine/detector/tone/coordinator ownership and the tone↔chromatic↔record↔playback interlock into explicit intent methods — this both fixes the structural god-object and is the prerequisite for testing the transition bugs.
2. **Fix the three MED mode-transition bugs:** unconditional `syncToneMode(false)` on sheet dismiss restarting the mic (`:245`), missing chromatic-off teardown/reset (`:239`), and no engine re-sync on foreground when already granted (`:150`).
3. **Add mode-transition + haptic-edge tests** (currently zero `TunerView`/coordinator coverage), and delete or document the dead `RawPitchReadoutView`.
