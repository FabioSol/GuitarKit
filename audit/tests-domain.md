# Audit — Domain tests

**Scope:** `GuitarKitTests/Domain/` — Fretboard/FretboardTests; Harmony/{Chord, ChordVoicing, CircleOfFifths, DiatonicTriads, Key, PitchClass, Scale, SpelledNote}Tests; Instruments/InstrumentLibraryTests; Metronome/{BeatAccent, MetronomeSequencer, SubdivisionSequencer, Subdivision, TapTempo, TimeSignature}Tests; Music/{Capo, Note, PitchCalculator, PitchResolution, ReferencePitch, Temperament}Tests; Tuning/{TuningFeedback, TuningSession}Tests. Cross-referenced source under `GuitarKit/Domain/`.

**Health:** Strong, behavior-focused suite: tests drive the public API, use deterministic injected time (TapTempo, TuningSession), seeded synthetic frequencies, and meaningful set/cents assertions. Coverage of the "happy path" plus most documented edge cases is excellent. The real gaps are a handful of source behaviors that exist and ship but are exercised nowhere (`FretboardScale.descendingNotes`, `CircleOfFifths.clockwise(steps:)` with steps>1, the root-in-bass *suppression* branch in the voicing generator, several Scale/ChordQuality edge cases), plus a couple of weak or coincidentally-passing assertions.

## Test bugs & weak assertions

- [MED] `Domain/Harmony/ChordTests.swift:54-59` — `testDominantEleventh` asserts the set `[.c, .g, .aSharp, .d, .f]` but never asserts the **5th (G)** is *intentionally retained* while the 3rd is dropped; the negative check only covers `.e`. The set equality is correct, but the test's stated intent ("3rd omitted by convention") would be more robust paired with an explicit positive assertion documenting which omission is deliberate. Fix: add `XCTAssertTrue(cChord(.dominantEleventh).contains(.g))` and a comment, mirroring the `.f` negative check on `dominantThirteenth`.
- [MED] `Domain/Harmony/ScaleTests.swift:42-58` — `noteCount` is asserted only for pentatonic (5) and blues (6). The property is `type.semitoneOffsets.count` (Scale.swift:126), i.e. it counts the *recipe* length, NOT distinct pitch classes. No test pins that `notes`/`pitchClassSet` have no accidental duplicates (a recipe with a repeated offset would silently shrink the Set but keep `noteCount` high). Low risk for current scales but the invariant "noteCount == pitchClassSet.count" is untested. Fix: assert `Scale(...).pitchClassSet.count == Scale(...).noteCount` for a representative scale.
- [LOW] `Domain/Music/PitchResolutionTests.swift:52-57` — `test_guitarLowE_resolvesToE2` uses `accuracy: 1.0` cents against the rounded input `82.41`. A 1-cent tolerance is loose enough that a real ~3-cent resolution bug here would still pass. The exact-input tests elsewhere use 0.01; consider feeding the exact E2 frequency (`calc.frequency(of: E2)`) and tightening to 0.01, keeping the 82.41 case as a separate "real-world rounded input" check.
- [LOW] `Domain/Harmony/ChordVoicingTests.swift:141-148` — `testStandardLibraryCMajorSoundsAllChordTones` asserts the *set* `[.c,.e,.g]` equals the sounded pitch classes; good, but it does not assert the bass note is C (root position), which `testCMajorGeneratedShapeIsRootPosition` only checks for the *generated* shape, not the curated x32010. Minor: the curated table's bass-note correctness is unverified. Fix: assert `voicing.playedNotes(on: board).first?.pitchClass == .c`.
- [LOW] `Domain/Metronome/TapTempoTests.swift:94-102` — comment on `test_slowTaps_clampAt30` says "1.5 s apart is 40 BPM (in range)" but the test never exercises 1.5 s; it jumps straight to a 3 s gap with a widened `resetGap`. The dead descriptive clause is slightly misleading. Harmless, but trim the comment to match what's tested.
- [LOW] `Domain/Tuning/TuningSessionTests.swift:130` — `XCTAssertNotEqual(session.deviationCents ?? 0, 0, accuracy: 0.0001)` — `XCTAssertNotEqual` with an `accuracy` asserts the values differ by *more than* 0.0001, an extremely loose floor for "far off." It passes trivially and doesn't really prove "far off." Fix: assert `abs(session.deviationCents ?? 0) > 100` (the locked high-E vs low-E gap is ~2400¢) to make the intent real.

## Coverage gaps (untested/weakly-tested behavior)

- **`FretboardScale.descendingNotes()` (FretboardScale.swift:65-67)** — never called by any test. `ascendingNotes()` is tested for sorting + membership, but the descending reverse and dedup-by-MIDI behavior of the descending path is unverified.
- **`CircleOfFifths.clockwise(from:steps:)` with `|steps| > 1` (CircleOfFifths.swift:54-64)** — every test goes through `next`/`previous` (steps ±1) or `distance`. The multi-step wrap arithmetic (`((index+steps)%count+count)%count`) and large/negative steps are untested. A multi-step jump that lands across the enharmonic seam is the riskiest path and has zero coverage.
- **Voicing root-in-bass *suppression* branch (ChordVoicingGenerator.swift:201, `guard rootString > 0 ... else return`)** — tests confirm C-major lands root-in-bass, but no test covers the documented case where no string in the window plays the root, so the bass is left as-is (the "gentle nudge, not a hard rule" branch). An assertion that a chord whose root is unreachable in the window still returns a non-empty, in-chord shape would lock this in.
- **`ChordVoicingGenerator.alternates` for a non-curated / minor chord** — `testAlternatesAreOrderedUpTheNeck` only uses C major. The "skip identical / skip all-muted" dedup logic (lines 137-143) and the high-fret behavior for chords like F#m (which `StandardChordLibrary` returns nil for) are untested.
- **`Chord.notes` ordering** — only `pitchClassSet` (unordered) is ever asserted. The documented "stacked order, root first" contract (Chord.swift:31) and the octave-wrap of >12 offsets at the *ordered* level are not directly tested (the 13th/9th wrap is verified only as set membership).
- **Scale `degree`/notes duplicate-safety & non-C roots for modes** — `FretboardScale.degree` (FretboardScale.swift:43-47) relies on `scale.notes.firstIndex`; modes are only degree-tested via the C-major fretboard. Harmonic/melodic minor and pentatonic *degree* numbering on the board is untested.
- **`PitchCalculator.cents` symmetry / NaN guards** — `test_cents_safeForSilence` covers `from: 0`; the `to: 0` / both-zero / negative-frequency inputs to `cents` are not covered (the public `cents` is reachable with arbitrary args).
- **`TimeSignature.noteValue` range / `sixEight` denominator** — labels assert "6/8" but no test asserts `TimeSignature.sixEight.noteValue == 8`; the noteValue field is only checked via the custom default (4) and equality. The preset denominators (the "/8" presets) are unverified beyond their label string.
- **`InstrumentLibrary` banjo/guitar7/bass5 preset note *sequences*** — banjo's reentrant 5th string (the classic high-G drone) is asserted only via `stringCount`, not its actual notes; `test_banjo_hasFivePegs` duplicates the count check in `test_stringCounts_matchTheKnownInstruments`. The banjo tuning's distinctive note layout is untested.
- **`CustomTuningSupport` (CustomTuningSupport.swift)** — no test exists under `Domain/`; coverage lives at `GuitarKitTests/Tuner/CustomTuning/CustomTuningTests.swift` (out of this audit's scope). Within the Domain tree this pure helper is unrepresented — fine if intentional, but worth noting since the file's own header points at a "CustomTuningTests" companion.

## Test quality & maintainability

- Determinism is excellent: `TapTempo` and `TuningSession` take injected timestamps; frequencies are derived from `PitchCalculator` rather than hard-coded magic, so they stay correct if the reference changes. The `test_allStringsLatched_reachesCompletion` index-based timestamp scheme (TuningSessionTests.swift:171-177) deliberately avoids float accumulation — good.
- Assertions are mostly meaningful and tight (0.01 Hz / 0.0001-cent tolerances). The drift tests (MetronomeSequencer/SubdivisionSequencer) over 10k–30k iterations are a genuinely strong property check, not a tautology.
- Minor duplication: `standardGuitar: [Note]` is re-declared verbatim in `CapoTests.swift:16`, `TemperamentTests.swift:17`, and built again in `FretboardTests`/`InstrumentLibraryTests`/`TuningSessionTests` via the library. A shared test fixture (e.g. `BuiltInTuning.standardGuitar`, already used by TuningSessionTests) would cut the repetition and prevent the hand-typed copies from drifting from the library.
- `BeatAccentTests`/`SubdivisionTests` lean on `allCases` exact-order assertions (e.g. BeatAccentTests:27, SubdivisionTests:24). These couple the test to declaration order — acceptable since the picker order is behavior, but worth a comment so a reorder isn't mistaken for a bug.
- No dead/disabled tests, no `XCTSkip`, no tautological `XCTAssertTrue(true)`. Helper functions (`n(...)`, `hz(...)`, `cChord(...)`) are clean and improve readability.

## Top 3 priorities

1. Cover the untested *branches* that ship today: `FretboardScale.descendingNotes`, `CircleOfFifths.clockwise(steps:)` for |steps|>1 and across the F♯/G♭ seam, and the voicing generator's root-in-bass *suppression* path (no reachable root).
2. Tighten the coincidentally-passing assertions: `TuningSessionTests.swift:130` (real "far off" check), `PitchResolutionTests.swift:52-57` (exact input + 0.01¢), and add the Scale `noteCount == pitchClassSet.count` invariant.
3. Broaden `alternates`/curated-library coverage beyond C major (minor + non-curated chords like F#m) and assert preset *note sequences* for banjo/guitar7, removing the duplicated banjo peg-count test.
