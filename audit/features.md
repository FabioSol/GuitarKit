# Audit — Features (Chords / Scales / Metronome / Circle of Fifths)
**Scope:** GuitarKit/Features/Chords/{ChordsView,ChordsViewModel}.swift, GuitarKit/Features/Scales/{ScalesView,ScalesViewModel}.swift, GuitarKit/Features/Metronome/{MetronomeView,MetronomeViewModel}.swift, GuitarKit/Features/CircleOfFifths/{CircleOfFifthsView,CircleOfFifthsViewModel,CircleWheelView,KeyDetailsPanelView}.swift

**Health:** The four tools are clean, well-structured, and consistent in house style; the @Observable view models keep musical truth in the pure engines and the audio teardown is mostly handled. The main real issues are (1) the Metronome's state-preservation claim being false under RootView's `switch`-based tool mounting, (2) heavy per-render recomputation of `currentVoicing`/`fretboardScale` across every grid cell, and (3) near-zero test coverage for three of the four view models. No retain cycles or playback-Task leaks found.

## Bugs & correctness
- [MED] `MetronomeView.swift:33` (with `RootView.swift:101-131`) — MetronomeView owns its model via `@State private var model`, but `currentToolScreen` is a `@ViewBuilder switch`, so navigating to another tool **tears the view down** and `.onDisappear { model.shutdown() }` fires, destroying the model and its tempo/time-signature/accents. The comment at `RootView.swift:111-112` and `MetronomeView.swift:31-34` both claim "the tempo survives navigating away and back" — it does not. The other three tools are correctly hoisted into `RootView` (`circleModel`/`chordsModel`/`scalesModel`, lines 36-38) precisely to survive this. Fix: hoist a `MetronomeViewModel` into `RootView` `@State` and inject it like the others, OR drop the false comments and accept reset-on-leave.
- [LOW] `MetronomeViewModel.swift:104,247-249` — `hapticsEnabled` is a plain stored `var` with no `didSet`, and `setHapticsEnabled` just assigns it. The header (lines 100-104) says the beat clock reads it "LIVE each beat," which the running `beatTask` does (line 337) — correct — but the very first beat after enabling won't lazily `prepare()` the generator until line 338's nil-check; `startBeatClock`'s eager prepare (lines 314-317) is skipped if haptics were off at start. Minor first-buzz latency, not a crash. Fine to leave, but worth a comment.
- [LOW] `MetronomeView.swift:90-91` — `.onChange(of: settings?.metronomeSoundSet)` fires `applyMetronomeSettings()` which calls `model.setSoundSet`; if the engine is playing this triggers `pushConfigAndRestartIfPlaying()` and snaps the click to beat 0. Combined with `.onAppear` (line 89) also applying settings, a tool re-entry while playing (not currently possible given the teardown bug above, but would be if hoisted) restarts the click. Acceptable given the documented "applies on next start" engine contract, but note it interacts with the fix above.
- [LOW] `ScalesViewModel.swift:41` / `ScalesView.swift` — `showFingerNumbers` is declared, documented as "behind a flag (default off)," and **never read anywhere** (no UI toggle, no use in `label(...)`). Dead code per the audit brief's "unused flags like finger numbers." Either wire a toggle or delete it.

## Efficiency
- [HIGH] `ChordsView.swift:162` — `cell(string:fret:)` calls `model.currentVoicing` for **every** cell. The grid is `stringCount × (fretCount+1)` ≈ 6×6 = 36 cells, and `currentVoicing` (`ChordsViewModel.swift:144-151`) rebuilds `alternateVoicings` each access — which runs `ChordVoicingGenerator.alternates(...)` **and** the `StandardChordLibrary` lookup (`:116-139`) every time. So ~36 full generator runs per render, plus more in `openMutedMarker`, `isRoot`, `label`, `nutBar`/`isOpenPosition`, and `voicingAccessibilityDescription`. Fix: compute the voicing/board once in `chordBox` (or cache on the model) and pass the resolved `ChordVoicing` + `Fretboard` into `cell`.
- [HIGH] `ScalesView.swift:126` — same pattern: `cell(string:fret:)` builds `let fs = model.fretboardScale` per cell, and `fretboardScale` (`ScalesViewModel.swift:84-86`) reconstructs the whole `Fretboard` + `FretboardScale` each call. With `fretCount = 12`, that's 6×13 = 78 reconstructions per render (plus `label(...)` calls). Fix: resolve `fretboardScale` and `fretboard` once in the `fretboard` view body, capture, pass down.
- [MED] `ChordsViewModel.swift:95-97,116` — `fretboard` and `alternateVoicings` are recomputed on every access with no memoization; `currentVoicing`, `voicingCount`, and `voicingAccessibilityDescription` each independently rebuild the list. Even one render touches it many times. A cached `@ObservationIgnored` cache invalidated on root/quality/capo/tuning change (or computing once per body) would remove the storm.
- [LOW] `MetronomeView.swift:174` — `.animation(.easeOut, value: model.currentBeat)` is attached **inside** the `ForEach` per dot, so all `beatsPerBar` dots animate on every beat change. Cheap, but the active-only scale/shadow already conveys it; could move up or key on `isActive`.

## Maintainability & practices
- [MED] Duplication across Chords + Scales view models: `LabelMode` enum (Chords:28 / Scales:23), the `instrument/standardTuning/currentTuning` init dance (Chords:81-87 / Scales:64-71), `activeTuning` (Chords:92 / Scales:76), `fretboard` (Chords:95 / Scales:79), the `tone`/`coordinator`/`playTask` audio trio (Chords:67-69 / Scales:55-57), and `stopPlayback` are essentially identical. Worth a shared `TuningAwareToolModel` base or a small `ToolPlayback` helper struct that owns the generator + coordinator + cancel logic. Also `stringDisplayOrder()` / handedness mirroring appears in both views.
- [MED] Degree-label logic is duplicated/divergent: `ChordsViewModel.degreeLabel(for:)` (`:220-237`) hand-maps semitones to `♭9/9/♭3…`, while Scales gets degrees from `FretboardScale.degree(...)` (`ScalesViewModel.swift:96`). Two different degree systems for sibling tools; consolidate into the domain so they agree.
- [LOW] `CircleOfFifthsView.swift` injects `viewModel` as `let` while the sibling tools use `@Bindable var model` — inconsistent, though correct here since the wheel only reads + calls methods (no `$` bindings). The header comment (lines 10-17) still says the view "OWNS the view model via `@State`," but `RootView.swift:36,118-119` actually owns and injects it — stale comment, should be corrected.
- [LOW] `KeyDetailsPanelView.swift:119-128` — comment promises a "fixed two-row arrangement" but the code is a single horizontally-scrolling `HStack`. Stale comment vs. implementation.
- [LOW] `CircleOfFifthsViewModel.swift:62-86` — `onPlayScale`/`onPlayChord` no-op hooks remain wired (called at `:110`) but the brief notes audio is owned per-tool elsewhere; with cross-links now the primary action these preview hooks are effectively dead. Confirm they're still intended.

## Test coverage gaps
- Only `CircleOfFifthsViewModel` has tests (`GuitarKitTests/Features/CircleOfFifths/CircleOfFifthsViewModelTests.swift`). **No** test target exists for `ChordsViewModel`, `ScalesViewModel`, or `MetronomeViewModel`.
- `ChordsViewModel`: untested `cycleVoicing` wrap-around (`:183-187`), `resetVoicing`, index clamping in `currentVoicing` (`:144-151`), the library-first fallback ordering and the all-muted placeholder path (`:116-139`), `degreeLabel` mapping, and `voicingAccessibilityDescription` string.
- `ScalesViewModel`: untested `activeTuning` override, `label(...)` for both modes, ascending/descending note plumbing.
- `MetronomeViewModel`: untested `bpm` clamp/recursion guard (`:47-61`), `resizeAccents` preserving choices on grow/shrink (`:265-275`), `cycleAccent` bounds guard, `nudge`, and `setCustomBeats` clamping. These are pure-logic and highly testable without audio.

## Top 3 priorities
1. Fix the Metronome state-preservation lie: hoist `MetronomeViewModel` into `RootView` `@State` and inject it (matching the other three tools), or remove the false "survives navigation" comments. (`MetronomeView.swift:33`, `RootView.swift:111`)
2. Kill the per-cell recompute storm in Chords and Scales: resolve `currentVoicing`/`fretboardScale` + `fretboard` once per render and pass them into `cell(...)`, and memoize `alternateVoicings`/`fretboard` on the models. (`ChordsView.swift:162`, `ScalesView.swift:126`)
3. Add view-model unit tests for Chords, Scales, and Metronome — especially the BPM clamp, accent resize, and voicing cycle/clamp logic — and remove the dead `showFingerNumbers` flag.
