# Audit — UI / Feature tests

**Scope:** `GuitarKitTests/Tuner/Capo/CapoLabelTests.swift`, `GuitarKitTests/Tuner/Chromatic/ChromaticZoneTests.swift`, `GuitarKitTests/Tuner/CustomTuning/CustomTuningTests.swift`, `GuitarKitTests/Tuner/HeadstockSpecTests.swift`, `GuitarKitTests/Tuner/Picker/InstrumentSelectionStoreTests.swift`, `GuitarKitTests/Features/CircleOfFifths/CircleOfFifthsViewModelTests.swift`, `GuitarKitTests/Settings/SettingsStoreTests.swift`, `GuitarKitTests/Snapshots/HeroSnapshotGenerator.swift`. Cross-referenced against the matching `GuitarKit/...` sources.

**Health:** The *pure* helpers (CapoLabel, ChromaticZone, CustomTuningSupport) and the three persistence stores are tested well — behavior-focused, deterministic, with good boundary/round-trip/reset coverage. The real risk is not in what's asserted but in what's *absent*: every genuinely UI/stateful surface (TuningSessionModel mode transitions, capo→target rebuild, latch/hold clock, navigation, cross-links) is untested, and the "snapshot" file is a non-asserting image generator that gives a false sense of UI coverage. Two shared-suite store cases are also order/parallelism-fragile.

## Test bugs & weak assertions
- [MED] `SettingsStoreTests.swift:26` & `InstrumentSelectionStoreTests.swift:28` — both cases use a *fixed* suite name (`"guitarkit.tests.settings"` / `"guitarkit.tests.picker"`) shared by every method in the class, cleaned only in `setUp`/`tearDown` — why: unlike `CustomTuningTests` which uses a per-test UUID suite (`CustomTuningTests.swift:59`), these rely on serial, non-overlapping execution. Under XCTest parallelization or a crash mid-test the shared plist leaks between tests, producing flaky, hard-to-reproduce failures. Both `@MainActor` cases also serialize all tests on the main thread, masking the issue today but not guaranteeing it. — fix: use a UUID-suffixed suite per test like `CustomTuningTests` does.
- [MED] `SettingsStoreTests.swift:42-66, 71-97, 136-160` — `confirmationSound`, `accent`, `metronomeSoundSet`, `metronomeHapticsEnabled`, and `experimentalFingerNumberLabels` are checked for their *default* only; they are never exercised in the persistence round-trip (`:71`) nor the reset symmetry (`:136`) tests — why: `reset()` (`SettingsStore.swift:447`) and the `didSet` persistence are hand-maintained lists; a setting dropped from `reset()` or given a wrong key would pass every existing test. The two metronome settings in particular have *zero* write/persist/reset assertions. — fix: add each non-default-only setting to both `test_writtenValues_persistAcrossNewStore` and `test_reset_restoresDefaults`.
- [LOW] `SettingsStoreTests.swift:113-123` — clamp tests assert the in-memory clamp but the comment "below the 415 floor / above the 466 ceiling" hardcodes the band in prose while asserting against `ReferencePitch.minHz`/`maxHz` — why: fine today, but `referencePitchHz` has a re-entrant `didSet` (`SettingsStore.swift:246-257`) that is the actual fragile logic; only the *result* is checked, not that the clamped value persists is covered (`:125` does cover persist — good). No bug, but the re-entrant clamp path deserves a direct test of a mid-range valid write persisting unchanged. — fix: add a "valid in-band value persists verbatim" assertion to pin the non-clamp branch.
- [LOW] `ChromaticZoneTests.swift:40-41` — `1.01` / `-1.01` are asserted `.inTune` to probe "just past ±1¢" — why: `1.01` is not exactly representable in `Double`; here it rounds *above* 1 so the test is robust, but using a literal a hair past an inclusive boundary is the classic place float representation bites. It happens to be safe (1.01 > 1.0) but the technique is fragile if thresholds change. — fix: prefer `perfectCents.nextUp` / `inTuneCents.nextUp` to express "smallest value past the boundary" intent-explicitly.
- [LOW] `CircleOfFifthsViewModelTests.swift:128-137` — `testNoCrashWhenPlaybackHooksAreNil` asserts hooks are nil then that selection sets the key — why: it does not actually assert the no-op *path* fires nothing (there's no spy proving `onPlayChord` was never invoked, since nothing invokes it anyway). It's really a duplicate of `testSelectingAKeyUpdatesSelection`. Low value but harmless. — fix: drop or merge; the meaningful guard is already `testPlayScaleHookFiresWithSelectedKeysScale`.
- [LOW] `HeroSnapshotGenerator.swift:106, 50-107` — the only assertions are `XCTAssertTrue(fileExists)` and `XCTFail` on render failure — why: these "tests" prove a PNG was written, not that it is correct, non-blank, or that `ImageRenderer` actually rasterized the SwiftUI hero (a known-broken renderer would still emit a valid PNG of a blank/placeholder view). They are correctly labelled "NOT a behavioral test" (`:5`), but they live in the test target and run on every `test` invocation, adding I/O and wall-time to CI for no pass/fail signal. — fix: gate behind an env flag or move out of the default test plan; at minimum assert non-trivial pixel content (e.g. image size > expected, or a non-uniform-color check).

## Coverage gaps (untested UI/state/persistence risk)
- **TuningSessionModel is entirely untested (HIGH).** `TuningSessionModel.swift` owns all the genuinely interesting UI state — `incrementCapo()`/`resetCapo()` (`:199`,`:205`), `select(instrument:)`/`select(tuning:)` (`:171`,`:180`), `reconfigure(...)` (`:187`), and `rebuildSession()` (`:214`) which re-derives targets through the capo. `CapoLabelTests` re-pins the *pure* `Capo.transpose` but nothing tests that `incrementCapo()` actually shifts the live session's targets or that the headstock peg notes follow the capo — the load-bearing integration the capo exists for. The class is injectable (`now:`/`haptics:` already faked in the snapshot file at `HeroSnapshotGenerator.swift:44-48`), so this is testable today with the same `FakeClock`.
- **The hold/latch beat clock & haptic edge-firing are untested (HIGH).** `fireHaptics()` (`TuningSessionModel.swift:129-153`) fires each milestone exactly once on a transition edge using `previousZone`/`wasComplete`. The snapshot file drives the clock to *produce* latched states (`HeroSnapshotGenerator.swift:60-75`) but asserts nothing about them — so "latch fires once", "completion flourish fires on false→true edge only", and "hapticsEnabled gates everything" are all unverified. A spy haptics provider + FakeClock would cover this cheaply.
- **Mode transitions (targeted ↔ chromatic) untested (MED).** `ChromaticZone.classify` is pinned, but the *switch* into chromatic mode and back (whatever owns the toggle) has no test; chromatic vs targeted threshold agreement is asserted only by shared constants, not by a session-level test.
- **Navigation & cross-links untested (MED).** No test exercises the nav stack, tool switching, or the Circle-of-Fifths → chord/scale cross-links. `CircleOfFifthsViewModelTests` covers the VM math only; `onPlayChord` (`CircleOfFifthsViewModel.swift:86`) is never wired or driven anywhere in tests.
- **Settings partial persistence (MED).** As noted above, `metronomeSoundSet`, `metronomeHapticsEnabled`, `accent`, `confirmationSound`, `experimentalFingerNumberLabels` lack round-trip/reset coverage — gaps in the very symmetry these store tests exist to guarantee.
- **`#if DEBUG debugShowDiagnosticsOverlay` reset is untested (LOW).** `SettingsStore.swift:464` resets it but `reset()` tests don't check it (it's deliberately non-persisted).
- **Snapshot approach is fragile, not sound (MED).** Per the file's own note (`HeroSnapshotGenerator.swift:147`), `ImageRenderer` can't rasterize `Form`/`List`/`NavigationStack`, so Settings and any nav-bearing screen are structurally un-snapshottable — the snapshot strategy can only ever cover leaf views, and even those are not diffed against a baseline, so visual regressions are invisible.

## Test quality & maintainability
- Strengths: tests assert *behavior/contracts* (badge strings, zone boundaries, round-trips, fall-backs) over implementation; boundary coverage in `ChromaticZoneTests` and `CapoLabelTests` is exemplary (every fret 1...12 looped, inclusive ±1/±3 edges probed). Store tests correctly inject `UserDefaults` and assert the subtle `true`-default-Bool-persists-`false` case (`SettingsStoreTests.swift:102`, `InstrumentSelectionStoreTests` round-trips). `CustomTuningTests` covers save/round-trip/replace/delete/isolation — a genuine persistence contract.
- The view-model tests (`CircleOfFifthsViewModelTests`) are meaningful: they pin the rotation-to-home geometry, shared-seat indexing, and scale-per-mode selection, and correctly *decline* to re-test the harmony domain.
- `#filePath`-relative output path in the snapshot generator (`HeroSnapshotGenerator.swift:97`) is a good portability touch.
- Weaknesses: inconsistent suite-naming discipline across the three store test files (UUID vs fixed); snapshot "tests" mixed into the behavioral target with no assertions; a couple of near-duplicate VM tests; threshold-edge tests using bare float literals rather than `nextUp`.

## Top 3 priorities
1. **Test `TuningSessionModel` behavior** — capo increment shifts live targets/peg notes, and the latch/completion haptics fire exactly once on their edges (use a spy `TuningHapticsProviding` + the existing `FakeClock`). This is the highest-value untested surface and is already injectable.
2. **Close the Settings persistence/reset gaps** — add `metronomeSoundSet`, `metronomeHapticsEnabled`, `accent`, `confirmationSound`, `experimentalFingerNumberLabels` to the round-trip and reset-symmetry tests so a dropped `reset()` line or wrong key fails a test.
3. **Make the store suites parallel-safe and de-risk the snapshots** — give `SettingsStoreTests`/`InstrumentSelectionStoreTests` per-test UUID suites (matching `CustomTuningTests`), and move `HeroSnapshotGenerator` out of the default test plan (or have it assert non-trivial pixel content) so CI isn't paying for a non-asserting image dump.
