# Audit — App shell & navigation
**Scope:** GuitarKit/GuitarKitApp.swift, GuitarKit/App/GKTool.swift, GuitarKit/App/RootView.swift, GuitarKit/App/ToolPlaceholderView.swift, GuitarKit/Navigation/RotaryNavBar.swift

**Health:** The shell is small, clean, and correct in its core flow (tuner-first launch, hoisted view models that survive navigation, exhaustive switch). The main weaknesses are in `RotaryNavBar`: it renders ~40 live glass coins every frame (most invisible) and recomputes a 40-slot dictionary on every render including every animation frame, which is the dominant performance risk in this layer. There is a duplicated/overridden `preferredColorScheme`, a stale header comment, and zero unit-test coverage for the nav's tricky pure geometry math.

## Bugs & correctness
- [MED] `RotaryNavBar.swift:101-134,140-143` — On `.onAppear`, `rotation` is set from `nearestRotation(for: selection)` but `GeometryReader`'s `center`/positions depend on `geo.size`, which is fine; however the apex layout is correct only because slot 0 sits at −90°. If `selection != tools[0]` at launch (it never is today — always `.tuner`, index 0), the wheel still spins to the right place, so no live bug — but the invariant "launch selection == first tool" is undocumented and fragile. Add a comment or assert so a future default change (e.g. remembering last tool) doesn't silently spin-in on first frame. Fix: document the dependency, or gate the instant placement on `!hasAppeared` rather than the implicit index-0 assumption.
- [LOW] `RootView.swift:144,151` vs `RotaryNavBar.swift:146-148` — Cross-link selection changes are wrapped in `withAnimation` in `RootView`, AND `RotaryNavBar.onChange(of: selection)` independently spins via its own `withAnimation`. Two animation transactions fire for one logical change (one drives the screen cross-fade, one the wheel). They happen to use the same 0.25s/spring curves separately, so it works, but it's two sources of truth for "animate this selection change." Not a crash; a coordination smell. Fix: let the nav own its spin animation and have RootView animate only the screen (it already does via `.animation(value:)` at line 56), dropping the explicit `withAnimation` wrappers.
- [LOW] `GuitarKitApp.swift:28` + `RootView.swift:69` — `.preferredColorScheme(.dark)` at the App scene is unconditionally overridden by `RootView`'s `.preferredColorScheme(settings.theme.colorScheme)`. The App-level modifier is dead code: when `theme == .system` RootView passes `nil`, which overrides `.dark`, so the documented "dark-first default" is NOT actually applied — a `.system` user gets system appearance, not dark. This contradicts the comment at GuitarKitApp.swift:23-27. Fix: drop the App-level modifier and make `AppTheme.system` resolve to `.dark` if dark-first is the real intent, or remove the dark-first claim.

## Efficiency
- [MED] `RotaryNavBar.swift:125-129,197-208` — All `slotCount = tools.count * copies = 5 * 8 = 40` coins are always instantiated as `Button`s, each carrying `.gkGlass(in: Circle())`. Liquid Glass is an expensive GPU material; ~33 of the 40 panes are at `opacity(proximity)` ≈ 0 yet still composited/rendered each frame. `opacity(0)` does NOT free the render pass. This is the single biggest cost in the file. Fix: skip rendering off-arc slots entirely — compute `proximity` first and return `EmptyView()` (or use a `where` clause / conditional in the `ForEach`) for coins below the hit-test threshold, so only the ~7 visible coins ever instantiate glass. The doc comment's worry about "insert/remove pops" can be mitigated by keeping stable `.id(k)` on the small visible set, or accepting that fully-transparent coins carry no visual continuity to lose.
- [MED] `RotaryNavBar.swift:115,220-230` — `representativeSlots()` runs an O(slotCount) loop building a dictionary, and it's called inside `body` (line 115) so it re-runs on EVERY body evaluation. During a spin, `rotation` is a `@State` animated value, so `body` re-evaluates each frame → the dict is rebuilt ~60×/sec, plus the `ForEach` rebuilds 40 coins each frame. Combined with the 40 glass panes this is a re-render storm on every navigation. Fix: the representative-slot mapping only matters for VoiceOver and changes meaningfully only when the settled selection changes, not mid-spin — compute it from `selection` (cheap, closed-form: nearest slot per tool) rather than scanning all slots against the live `rotation`, or memoize keyed on the rounded rotation.
- [LOW] `RotaryNavBar.swift:258,222` — Both `nearestRotation` and `representativeSlots` loop the full `slotCount`. `nearestRotation(for:)` is also called from `onChange` per selection (fine), but its inner loop recomputes `slotAngle(k)` and a `normalizeToShortest` for all 40 slots when only `copies` slots (8) actually show the target tool — the `where` clause filters after the modulo, so it's already limited to 8 iterations; acceptable. No change needed beyond awareness.

## Maintainability & practices
- [MED] `RotaryNavBar.swift:21` — Header comment claims "The chrome is Liquid Glass, grouped in a `GlassEffectContainer` so the tabs blend/morph as they move." The code does NOT use `GlassEffectContainer`; each coin uses its own `.gkGlass` (and the in-body comment at lines 122-124 explicitly explains why they're NOT fused). The header is stale and contradicts the implementation. Fix: update the header to match (per-coin glass, no container, and why).
- [LOW] `ToolPlaceholderView.swift` — This view is now dead code: `RootView.currentToolScreen` (lines 103-131) routes every one of the five cases to a real view; nothing constructs `ToolPlaceholderView` except its own `#Preview`. The header still describes it as "used for all five tools." Fix: delete the file (and its preview), or keep it only if intentionally retained as a scaffold and say so.
- [LOW] `RotaryNavBar.swift:75,92,97` — `copies = 8`, `radius = 480`, `centerYOffset = 415` are tuned magic numbers with interdependencies (visible arc width depends on all three plus `itemSize`). They're commented, but there's no single derived relationship, so changing one silently breaks the "~7 visible coins" assumption in `visibleHalfAngle` (line 87). Acceptable for now; consider deriving `visibleHalfAngle` and `copies` from a target "visible coin count" constant.
- [NIT] `RotaryNavBar.swift:236-239` — `select(_:)` guards `tool != selection` then sets the binding; the spin is performed by `onChange`. Clean, but the guard duplicates the `guard` already implicit in `onChange` only firing on real changes. Minor.

## Test coverage gaps
- [HIGH] No tests exist for `RotaryNavBar`'s pure geometry/selection math, despite a rich existing test suite (133 swift files, ~45 test files) covering every Domain unit. The following are pure, deterministic, and trivially testable but UNTESTED:
  - `normalizeToShortest(_:)` (line 277) — the boundary behavior (`d > 180` vs `d <= -180`, exact ±180) is the heart of "shortest path + wrap" and is easy to get wrong. Test ±180, ±181, ±359, 360, 0.
  - `nearestRotation(for:)` (line 255) — should always return a rotation within (−180,180] of current and land the target tool at the apex; verify shortest-path selection when the same tool appears in 8 slots.
  - `slotAngle(_:)` (line 214) and the `tools[k % count]` slot→tool mapping — verify slot 0 → apex/tuner and wrap-around.
  - `representativeSlots()` (line 220) — exactly one slot per tool, each the nearest to apex.
  These are static/`nonisolated`-friendly; extracting them to a free `enum WheelGeometry` namespace would make them testable without a SwiftUI host. Fix: add a `RotaryNavBarGeometryTests`.
- [LOW] `RootView` cross-link funcs (`openChordInChordsTool`, `openScaleInScalesTool`, lines 140-152) mutate model + selection; no test asserts model state is loaded BEFORE selection flips. A small view-model-level test (the models are `@Observable`) would lock in the slice-#21 contract.

## Top 3 priorities
1. Stop rendering ~33 invisible glass coins and rebuilding the 40-slot dict every frame (`RotaryNavBar.swift:125-129,115,220`) — gate coin instantiation on visibility and compute representative slots from `selection`, not live `rotation`.
2. Add unit tests for the nav's pure math (`normalizeToShortest`, `nearestRotation`, `slotAngle`, `representativeSlots`) — extract to a testable namespace.
3. Resolve the `preferredColorScheme` override (GuitarKitApp.swift:28 vs RootView.swift:69) so "dark-first" is real or the claim is dropped; fix the stale `GlassEffectContainer` header and delete dead `ToolPlaceholderView`.
