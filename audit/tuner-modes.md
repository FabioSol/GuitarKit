# Audit — Tuner modes (capo / chromatic / custom tuning / haptics / picker)
**Scope:** GuitarKit/Tuner/Capo/{CapoControlView,CapoLabel}.swift; GuitarKit/Tuner/Chromatic/{ChromaticReadoutView,ChromaticZone,HeroFlipModifier}.swift; GuitarKit/Tuner/CustomTuning/{CustomTuningStore,CustomTuningEditorView}.swift; GuitarKit/Tuner/Haptics/TuningHaptics.swift; GuitarKit/Tuner/Picker/{InstrumentPickerView,InstrumentSelectionStore,InstrumentSelectorPill}.swift (plus supporting Domain types).

**Health:** The slice is in good shape: clean view/model separation, pure testable helpers (`CapoLabel`, `ChromaticZone`, `CustomTuningSupport`), and disciplined UserDefaults stores with injectable suites and decode-failure fallbacks. The real issues are concentrated in a few interaction/accessibility seams (overlapping capo gestures, a VoiceOver decrement that jumps to zero, untestable view-side capture/save logic) rather than in the persistence core. No data-loss or crash bugs found in the stores.

## Bugs & correctness
- [BUG|MED] `CapoControlView.swift:87,109,112` — Three gesture recognizers compete on the same pill: the x's `.onTapGesture { onReset() }` (child), the pill's `.onTapGesture { onIncrement() }`, and `.onLongPressGesture { onReset() }`. The comment at :84-86 claims the x uses a "high-priority tap so tapping the x clears instead of incrementing", but no `.highPriorityGesture`/`gesture(_:including:)` is used — it's a plain `.onTapGesture` on the child stacked under the parent's tap. SwiftUI's resolution of an inner vs. outer plain `onTapGesture` is order/hit-test dependent and not guaranteed to favor the child; a tap on the x can increment instead of reset. Fix: make the x a real `Button`/`.highPriorityGesture`, or drop the x's own tap and rely solely on the adjustable action + long-press, so reset has one unambiguous owner.
- [BUG|MED] `CapoControlView.swift:132-137` — VoiceOver `.decrement` maps to `onReset()` (jump straight to fret 0), not a single-fret decrement. So a VoiceOver user swiping down on a capo at fret 5 lands on 0, while swiping up moves by 1 — asymmetric and surprising for an "adjustable" stepper, where increment/decrement are expected to be symmetric ±1 steps. The label will then announce "No capo" after one down-swipe, which reads as a bug to an assistive-tech user. Fix: add an `onDecrement` callback (owner does `Capo(fret: capo.fret - 1)`), reserving reset for the explicit x / long-press / a custom accessibility action.
- [BUG|LOW] `CustomTuningEditorView.swift:142-145` — Capture writes `detectedNote()` into the slot only when non-nil and gives NO feedback when the mic returns nil (silence/low clarity): the button appears to do nothing. Combined with the flagged-as-basic hear/capture audio-session interplay, there's no indication whether capture succeeded, no debounce, and no guard that the captured note is plausible for that string. Fix: surface a transient "didn't hear a note" state (or disable the mic button when `detectedNote()` is nil), and confirm the presenter actually arms the detector/session while the editor is open.
- [BUG|LOW] `ChromaticReadoutView.swift:68` — `.animation(.easeOut, value: reading)` animates on `PitchReading` equality. Because `frequency`/`centOffset` are continuous, nearly every detector frame changes `reading`, so this fires an implicit animation every frame — and it also animates the idle↔live transition of the big note. Functionally fine but means the note/cents are perpetually mid-animation under live input (slight lag/smear). Consider keying the animation on `zone` (or `note.name`) rather than the whole reading.
- [BUG|LOW] `HeroFlipModifier.swift:50-58,38-39` — The header comment (:38-39) says faces are "stored as closures we call inside `body` so SwiftUI builds each face lazily." They are not: `init` calls `front()`/`back()` eagerly and stores the resulting `View` values. Both faces are always built (the crossFade/rotation paths also keep both in the hierarchy). This is correct behavior for a flip card but the "lazy" claim is misleading and could mislead a maintainer into thinking an off-screen face is skipped.

## Efficiency
- `InstrumentSelectionStore.swift:113-115,166-174` — every `recordSelection` rewrites the entire `usageCounts` dictionary to UserDefaults via `didSet`; `recordSelection` also triggers three separate synchronous writes (lastInstrumentID, lastTuningName, usageCounts) per selection. Tiny data, acceptable, but worth noting as the pattern scales.
- `CustomTuningStore.swift:235-238` — re-encodes and writes the whole library JSON blob on every save/delete. Documented and fine at this size.
- `InstrumentPickerView.swift:247-264` — `instrumentTunings` filters `instrument.tunings` once per category (4 passes) for every expanded row. Negligible for preset counts; a single `Dictionary(grouping:)` would be tidier if lists grow.

## Maintainability & practices
- `CapoControlView.swift:84-88` — comment asserts a behavior ("high-priority tap") the code does not implement (see BUG above). Stale/aspirational comments on gesture priority are a trap; align comment and code.
- `InstrumentPickerView.swift:411` — preview copy "(no-op until slice #12)" is dead/stale now that slice #12 (custom tuning) exists and is wired. Minor doc rot.
- `InstrumentPickerView.swift:260,274` / custom-tuning rows — `ForEach(presets, id: \.name)` and customs `id: \.name` rely on name uniqueness. For built-in presets that holds; for customs the store enforces unique names per instrument (`save` replaces by name), so this is consistent — but the coupling is implicit. Worth a one-line note that name is the stable identity end-to-end (store + ForEach + delete all key on name).
- `CustomTuningStore.swift:103` / `InstrumentSelectionStore.swift:49-53` — keys are versioned/namespaced well (`.v1`). No migration path exists yet; the decode-failure-to-empty fallback (CustomTuningStore:148-155) silently DISCARDS unreadable data. That's the right call for resilience but means a future schema bump that changes the DTO shape will silently wipe saved tunings rather than migrate them. Document that a DTO change requires a new key + read-old-then-migrate, not an in-place edit.
- `CustomTuningEditorView.swift:173` / `CustomTuningStore` — editor builds `Tuning(category: .alternate, ...)` and the store also forces `.alternate`; two places encode the same "custom == alternate" rule. Single-source it (e.g. a shared constant) so they can't drift.
- `InstrumentSelectionStore.swift:113-115` — `usageCounts` grows unbounded (one key per ever-selected instrument). Bounded by library size today, so fine; flag only if instruments ever become user-generated.

## Test coverage gaps
- Capo gesture/accessibility behavior is UNTESTED: the increment-clamp-at-12 and the decrement→reset mapping live in the view (`CapoControlView`) with no test. `CapoLabelTests` thoroughly covers the pure label/clamp/transpose but not the interaction contract (tap = +1, x/long-press = reset, VoiceOver decrement behavior). The BUGs above would not be caught by the current suite.
- `CustomTuningStore` lacks a CORRUPT/UNDECODABLE-data test: there's no test that writing garbage under `guitarkit.customTunings.v1` yields an empty library rather than a crash (the resilience path at :148-155). Also no test for the delete-empties-key cleanup (:219-221) leaving the map without a stale empty array.
- `CustomTuningEditorView.save()` blank-name fallback (:168-175) and the mic-capture nil path (:142-145) are untested (view logic). At minimum extract `save`'s name resolution is already pure via `CustomTuningSupport.autoSuggestedName`, but the trim→fallback branch itself has no coverage.
- `ChromaticZone` is well tested; `ChromaticReadoutView.accessibilityPhrase` (cents rounding, sharp/flat wording) is not — a pure-ish function worth pinning.
- No test asserts `recordSelection` round-trips `lastTuningName` AND bumps usage in one call atomically (covered partially; the "never drift apart" guarantee at :157-174 isn't directly asserted together).

## Top 3 priorities
1. Fix the capo x/tap gesture ambiguity (`CapoControlView.swift:87,109`) — make reset an unambiguous owner (real Button / highPriorityGesture) so tapping the clear icon can't increment.
2. Fix the VoiceOver decrement (`CapoControlView.swift:132-137`) to step −1 instead of jumping to reset, restoring symmetric adjustable behavior; add interaction tests for the +1/−1/reset contract.
3. Add a corrupt-data resilience test for `CustomTuningStore` and document the no-migration / silent-discard tradeoff so a future DTO schema change doesn't quietly wipe saved tunings.
