# Audit — Settings
**Scope:** GuitarKit/Settings/SettingsStore.swift, GuitarKit/Settings/SettingsView.swift

**Health:** The store is well-structured and the load/persist/reset symmetry holds for every persisted property — no key collisions, no property missing from `init` or `reset()`, and the `loadBool`/`loadEnum` helpers correctly distinguish "missing" from "explicitly set." No correctness bugs found. The remaining items are minor maintainability points: redundant `didSet` re-persistence during init, a small clamp-comparison fragility, and a couple of test-coverage gaps (most notably no test for the unrecognised-raw-value enum fallback, which is the single most failure-prone branch).

## Bugs & correctness
- No bugs found. Every persisted property (`referencePitchHz`, `sweetenedTuningEnabled`, `inTuneSensitivity`, `hapticsEnabled`, `soundEnabled`, `confirmationSound`, `theme`, `accent`, `handedness`, `defaultLabeling`, `metronomeSoundSet`, `metronomeHapticsEnabled`, and all three `experimental*` flags) appears consistently in the `Key` enum, `Default` enum, a `didSet` writer, the `init` loader (`SettingsStore.swift:390-439`), and `reset()` (`SettingsStore.swift:447-466`). `debugShowDiagnosticsOverlay` (`:364`) is intentionally non-persisted and is correctly excluded from `init`/load but still reset in `reset()` (`:464`) — consistent with its documented "resets every launch" contract.
- [LOW] `SettingsStore.swift:250` — the clamp guard compares `clamped != referencePitchHz` with `!=` on `Double`. For a NaN write this works only by luck: `ReferencePitch(hertz: .nan)` returns `466.0` (verified), so `466 != nan` is true, the property is reassigned to `466`, and on the re-entrant pass `466 == 466` stops the recursion. It is safe today, but the safety depends on `ReferencePitch` never returning NaN. If that invariant ever weakened, `NaN != NaN` being always-true would cause unbounded `didSet` recursion. Consider clamping defensively against non-finite input (e.g. `guard referencePitchHz.isFinite` early) to make the safety explicit rather than incidental.

## Efficiency
- [LOW] `SettingsStore.swift:390-439` — every loaded property is *assigned* in `init`, which fires each `didSet` and re-writes the just-read value back to `UserDefaults`. This is documented and intentional (seeds defaults on first launch), and the cost is ~15 trivial writes once per launch — negligible. Noted only for completeness; no action needed unless launch-time `UserDefaults` writes ever show up in profiling.
- `referencePitchHz`'s clamp path (`:251-254`) re-enters `didSet` once on an out-of-range write. Cheap and documented; fine.

## Maintainability & practices
- [MED] `SettingsView.swift:120-124` (Appearance) and `:153-157` (Metronome) — `ForEach` iteration is inconsistent across pickers. Theme/Handedness/Labeling/Sensitivity/ConfirmationSound iterate `ForEach(SomeEnum.allCases)` relying on the enum's `Identifiable` conformance, but `metronomeSoundSet` uses `ForEach(MetronomeSoundSet.allCases, id: \.self)`. The reason is that `MetronomeSoundSet` (in Audio/ClickSound.swift) is `Hashable` but not `Identifiable`, whereas the Settings-local enums are `Identifiable`. The picker also calls `set.label` here vs `.displayName` everywhere else. Both work, but the divergence is a foot-gun for the next reader — consider giving `MetronomeSoundSet` an `Identifiable`/`displayName` shim or documenting why it differs.
- [LOW] `SettingsStore.swift:124-134` — `AppAccent` is a single-case enum that is persisted, loaded, and reset but never surfaced in the UI (the view comment at `SettingsView.swift:115-117` explains this is intentional forward-compat). Flagged per the brief's exclusion list as INTENTIONAL — keeping for the record, not for action.
- [LOW] `SettingsView.swift:245-253` — two `TODO`-stubbed buttons ("Rate GuitarKit", "Contact Support") have empty actions. They render as tappable rows that silently do nothing, which is a minor UX wart until wired. Acceptable as tracked follow-ups (#22) but worth a `.disabled(true)` or "coming soon" affordance in the interim so users aren't tapping dead controls.
- [LOW] `SettingsView.swift:38` — `@Environment(\.dismiss) private var dismiss` is read but never used in this view (the comment says it's "kept here for completeness" for a presenter-supplied toolbar). This is dead code in the view as written; the dismiss should live in whatever presents the sheet, not here. Harmless but will draw an unused-warning eye.

## Test coverage gaps
- [MED] No test covers `loadEnum`'s unrecognised-raw-value fallback (`SettingsStore.swift:493-496`) — the branch where a persisted string no longer maps to any enum case (e.g. a case removed in a future version). This is the helper's whole reason to exist and its most failure-prone path. Add a test that writes a garbage string to, say, `Key.theme` and asserts a new store falls back to `.system`.
- [MED] No persistence/reset coverage for `metronomeSoundSet`, `metronomeHapticsEnabled`, `experimentalFingerNumberLabels`, `experimentalReactiveBackdrop`, `confirmationSound` round-trip beyond the one set in `test_writtenValues_persistAcrossNewStore`, or `accent`. The round-trip and reset tests exercise a representative subset but skip the metronome group and two of three experimental flags entirely — a regression that broke (e.g.) the metronome keys would pass CI.
- [LOW] No test asserts that a *fresh* store seeds defaults into the backing `UserDefaults` (the init-writes-back behaviour relied on at `:386`). If that ever changed silently, nothing would catch it.
- [LOW] `referencePitchHz` clamp is tested at both extremes and for persistence, but not for a NaN/non-finite write — see the `:250` note above.

## Top 3 priorities
1. Add a `loadEnum` unrecognised-raw-value test (write garbage to a `String`-backed key, assert default fallback) — covers the store's most fragile branch (`SettingsStore.swift:493-496`).
2. Extend persistence + reset tests to the metronome group and the two untested experimental flags so a broken key/`didSet` can't pass CI.
3. Reconcile the picker inconsistency in `SettingsView.swift` (`metronomeSoundSet` using `id: \.self`/`.label` vs every other picker's `Identifiable`/`.displayName`) by giving `MetronomeSoundSet` an `Identifiable`/`displayName` shim.
