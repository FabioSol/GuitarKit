# Audit — Domain/Pitch (DSP)
**Scope:** GuitarKit/Domain/Pitch/{MPM.swift, YIN.swift, PitchAlgorithm.swift, PitchPreprocessor.swift, PitchSmoother.swift}

**Health:** The math is competent and the comments are excellent. The single-detector cores (MPM/YIN) are close to textbook-correct, but two real correctness issues exist (an ensemble "agree" branch that can return YIN's frequency while attributing MPM's clarity, and a `keyMaxima` boundary that can drop the final hump / re-include flat-top neighbors). The hot path allocates several `[Float]` buffers per call (~10×/sec on 4096 samples), which is the most impactful efficiency problem. Test coverage validates happy-path synthetic tones well but has almost no coverage for the numerically delicate edges (disagreement/octave handling, filter transients, NaN/Inf, near-Nyquist, parabolic edge cases).

## Bugs & correctness

- [BUG|HIGH] `PitchAlgorithm.swift:104-107` — On AGREEMENT the comment says "take the better-located estimate," but the code returns `best.frequency` where `best = m.clarity >= y.clarity ? m : y` — i.e. it picks by **clarity**, not by location. Worse, the clarity reported is `max(m.clarity,y.clarity)+0.1` regardless of which frequency was chosen, so you can return YIN's frequency with MPM's (higher) clarity, or vice-versa. When the two disagree by up to 40 cents this picks an essentially arbitrary one of the two. Why it matters: 40 cents is ~半 a quarter-tone — for a tuner that's a visible needle error, and the "corroboration boost" is applied even when they're 39 cents apart. Fix: when corroborating, return a single well-defined frequency (e.g. clarity-weighted mean, or the higher-clarity detector's frequency *and* its own clarity, boosted) — don't mix one detector's freq with the other's clarity.

- [BUG|MED] `MPM.swift:222-244` — `keyMaxima` can both **miss the final hump** and **mis-handle flat tops**. The hump is only flushed (lines 234-243) when the curve next goes `<= 0`. The trailing flush at 246-248 covers a hump open at the very end, but the local-max test at line 225 requires `nsdf[i] > nsdf[i-1] && nsdf[i] >= nsdf[i+1]`; a peak sitting exactly at `i == maxLag-1` whose neighbor `nsdf[maxLag]` is larger will never be recorded as the hump's max, and `currentMaxIndex` stays 0 → the hump is silently dropped even though it may contain the fundamental for a low note whose period is near the buffer length. Also, because a hump's max is taken as the first strict local max found, a flat-topped NSDF peak (common after band-pass filtering removes high harmonics) records its **left edge**, biasing the lag low (pitch high) before parabolic refine. Fix: track running max over the whole hump regardless of the local-max predicate (just `if nsdf[i] > nsdf[currentMaxIndex]`), and treat `currentMaxIndex == 0` sentinel carefully (lag 0 is a valid index, though excluded here by the minLag skip — still fragile).

- [BUG|MED] `MPM.swift:221,226` — `currentMaxIndex == 0` is used as the "no peak yet" sentinel, but `0` is also a valid array index. It's safe today only because Step A/B skip past lag 0; if `keyMaxima` is ever called with `minLag <= 0` or the skip logic changes, index 0 becomes ambiguous. Use `-1` or `Int?` as the sentinel.

- [BUG|MED] `MPM.swift:177` / `YIN.swift:82-83` — `prefix[overlap]` and `totalEnergy - prefix[tau]` are mathematically the two overlap energies, but they are **not** the same sum range. `prefix[overlap] = Σ_{j<overlap} x[j]²` and `totalEnergy - prefix[tau] = Σ_{j≥tau} x[j]²` (which has `n - tau = overlap` terms — correct count, but the *second* window is `x[tau..<n]`, i.e. indices `tau … n-1`, matching `x[j+τ]` for `j<overlap`). This is actually correct — flagging only to note it's load-bearing and untested at the boundary `tau == maxLag` where `overlap` can be as small as 1; a single-sample dot product is fine but the parabolic refine then runs near the array edge. No fix needed; add a boundary test.

- [BUG|LOW] `MPM.swift:112` / `YIN.swift:123` — `Float(sampleRate) / chosen.lag` has no guard that `chosen.lag > 0`. Parabolic refinement (`MPM.swift:277-278`, `YIN.swift:138-139`) adds `delta` which for a near-zero `denom` can be large; if `refinedLag` is driven to 0 or negative by a pathological 3-point set, this yields `+Inf` / negative frequency. The `denom != 0` guard catches exact zero but not near-zero (tiny `denom`, large `delta`). The downstream `frequency >= minFrequency` check would reject Inf, but NaN (`0/0` is guarded, but `Inf - Inf` style intermediates aren't) would pass `>=`/`<=` as false → nil, so it fails safe — but a clamp on `delta` (e.g. `|delta| < 1`) is the standard guard and is missing in both.

- [BUG|LOW] `PitchPreprocessor.swift:130-131` — `min(highPassHz, sampleRate/2 - 1)` clamps the cutoff to just under Nyquist, but does NOT guarantee `highPassHz < lowPassHz` after clamping at low sample rates. At, say, 2 kHz sample rate (unlikely but possible from a misconfigured route), both clamp to 999 Hz and the band-pass becomes degenerate (HP and LP at the same corner). No NaN, but silently wrong. Also no guard that `highPassHz <= lowPassHz` in `setCutoffs` (Tuner Lab can set them inverted). Fix: validate ordering.

- [BUG|LOW] `YIN.swift:103` — the "walk to the bottom of the dip" loop `while dPrime[tau+1] < dPrime[tau]` descends only while strictly decreasing. On a flat dip floor (`dPrime[tau+1] == dPrime[tau]`, plausible after filtering) it stops at the **first** sample of the flat region, biasing the lag and thus the parabolic minimum. Minor, but a real-audio-vs-synthetic divergence: synthetic sines won't produce flat floors, real filtered notes can.

## Efficiency

- [HIGH] Hot-path allocations. Per `detectPitch` call MPM allocates `prefix` (`n+1`), `nsdf` (`maxLag+1`), and a `peaks` array; YIN allocates `prefix`, `d`, `dPrime`. At ~10 calls/sec on 4096 samples (and **2×** for `.ensemble`), that's ~10+ heap arrays/sec churning. `PitchPreprocessor.process` (`:125`) allocates a **new** `[Float]` via `samples.map` every buffer too. None of these are reused. Recommendation: hoist scratch buffers into a reusable detector context (the algorithms are `enum` namespaces — they'd need to become small `struct`s holding scratch, or take an `inout` scratch param) so steady-state detection is allocation-free.
- [MED] `PitchSmoother.push` (`:76`) calls `window.sorted()` every buffer — allocates a new array each call. Trivial for `windowSize=5`, but it's on the per-buffer path; an insertion-sorted ring buffer avoids the allocation.
- [LOW] `vDSP_dotpr` is used well (the one genuinely vectorized op). The prefix-sum and `dPrime` loops are scalar Swift; for 4096 samples that's fine, but `vDSP_vsq`+`vDSP_vswsum` (or a running `vDSP` cumulative) could vectorize the prefix sum if profiling shows it hot.

## Maintainability & practices

- MPM/YIN duplicate the entire prefix-sum + `vDSP_dotpr` autocorrelation block (`MPM.swift:151-181` ≈ `YIN.swift:68-86`). Extract a shared `autocorrelationAndEnergies` helper — reduces the chance the two drift and keeps the boundary math in one tested place.
- The two parabolic refiners (`MPM.parabolicPeak`, `YIN.parabolicMinimum`) are the same parabola-vertex formula. Share one.
- `PitchAlgorithm.ensemble` hard-codes the 40-cent agreement window and the `+0.1` clarity boost as magic numbers inline (`:104,107`); promote to named constants with the rationale, like MPM/YIN do for their thresholds.
- MPM's clarity is the NSDF height; YIN's is `1 - d'`. The comment claims they're "the same 0…1 scale," but they are not directly comparable distributions — the ensemble's `>=` clarity comparison (`:106,109`) implicitly assumes they are. Worth documenting/validating that the two clarity scales are calibrated against each other, since the ensemble's tie-break depends on it.

## Test coverage gaps

- **Ensemble disagreement / octave error is completely untested.** The most valuable ensemble behavior — one detector makes an octave error, the other doesn't, and the ensemble must pick correctly — has no test. Add: MPM-vs-YIN disagreeing by >40 cents, assert the chosen one; and an agreement case asserting *which* frequency is returned (would have caught the `PitchAlgorithm.swift:104` bug).
- **Filter transient / state across buffers untested.** `PitchPreprocessor` is stateful (biquads carry delay memory) but no test feeds two consecutive buffers and checks continuity, nor checks `reset()` actually clears state, nor that a sample-rate change rebuilds. The comment "no per-buffer transient" is an untested claim. Add a buffer-boundary continuity test and a `reset()`-clears-transient test.
- **Biquad coefficients unverified.** No test checks the RBJ coefficients directly (e.g. DC gain of LP ≈ 1, DC gain of HP ≈ 0, Nyquist gain of HP ≈ 1). Tests only check gross RMS gain at three frequencies. A wrong sign in `b1` would still pass the RMS tests at some frequencies. Add coefficient/impulse-response assertions.
- **No NaN/Inf input tests** for any detector or the smoother. Feed `[.nan]`/`[.infinity]` and assert graceful nil / no crash.
- **Near-min/near-max frequency edges** under-tested: maxFrequency maps to `minLag = max(2, …)` — test a tone at exactly `maxFrequency` (1500 Hz) and just below `minFrequency`. The `maxLag > minLag` guard (`MPM:90`, `YIN:63`) has no test that exercises the rejection.
- **`keyMaxima` final-hump / flat-top cases** untested (the BUG above). Add a synthetic NSDF with a peak at the last in-range lag.
- **PitchSmoother even-window / median tie behavior** untested; the early-fill window (`count < windowSize`) median index choice is asserted nowhere.

## Top 3 priorities
1. Fix the ensemble agreement branch (`PitchAlgorithm.swift:104-107`): stop returning one detector's frequency with the other's clarity; define corroboration precisely — and add the disagreement/octave-error tests that would have caught it.
2. Harden `MPM.keyMaxima` (`:221-248`): track the hump max unconditionally, fix the `0`-as-sentinel ambiguity, and guarantee the final hump is flushed; add a last-lag-peak test.
3. Remove hot-path allocations (reusable scratch buffers in MPM/YIN/Preprocessor) since these run ~10×/sec (2× for ensemble) on 4096-sample buffers.
